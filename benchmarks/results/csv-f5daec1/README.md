# CSV comparison — 2026-11-06

First measurement of the CSV structural-index kernels against the Java CSV field and native
references. One `csv_measure` run per binary on shared BuildBuddy RBE workers.

**Shared-host timings are advisory.** Every number comes from one run on shared machines. The
figures are not confidence intervals, and they do not support precise speedup claims. Each
Bazel shard ran on its own worker, so comparisons are valid only **within one shard** (one
dataset at one size, or the sweep). Never compare across shards. The workers were a mix of
`AMD EPYC` and `Intel Xeon @ 2.70/3.10 GHz` hosts, and all of them reported AVX-512, so `native`
dispatch picked AVX-512BW everywhere. The AVX2 and SWAR native kernels were measured by forcing
them. The hosts are listed in [`csv-comparison.md`](csv-comparison.md).

Java allocation figures come from the thread allocation counter, and they repeat exactly
across forks. They exclude native memory. The native kernels allocate none; the FFM copy path
uses a reused native buffer.

## Files

- `raw/csv-<binary>-<group>.json`: every cell's raw samples (five time samples of at least 0.3 s,
  three allocation samples, two fresh-process forks per cell), the fixture SHA-256, checksums,
  the native probe rows from the same worker, `/proc/cpuinfo` and the SVM binary hash.
- [`csv-comparison.md`](csv-comparison.md): every cell, generated by
  `python3 benchmarks/comparison/csv_report.py raw/*.json`.
- `local-arm64/`: an advisory local run on an Apple M5 Max (macOS, JVM plus a NEON C++ probe),
  taken with `run.sh` and `LocalBench.java`, which are kept here. It is not a harness result: no
  forks and no allocation counter.

## Caveats specific to this run

- Fixtures are synthetic. They are generated from a seed and checked by SHA-256 against the
  native probes' input. Real files differ in field width, quoting density and line endings (the
  fixtures use LF only).
- Truffledata validates UTF-8 strictly in the `strings` and `typed` paths: the Java validator
  for Java kernels, simdutf for native kernels. The competitors decode leniently and replace
  malformed input. The `scan` workload validates nothing on any engine.
- `strings` materializes a `java.lang.String` per cell. The Rust `csv-string-record` row
  validates UTF-8 into a reused `StringRecord`. It does not allocate an owned string per
  field, so it is a reference point, not a like-for-like competitor.
- Rust `csv-typed` parses with `str::parse`. Its checksum equals the Java engines' checksum, so
  the work is cross-checked.
- In the `kernel-*` rows, the indexed scanner and the decoding run inside the harness. These
  paths are not yet wired into `Csv.parse` or `CsvPlan` (the "current library" rows). They show
  what the seam integration can reach, not shipped behavior.
- The size sweep ran one fork per point. Read it for crossovers, not absolute values.
