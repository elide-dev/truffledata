## Task R1: fat-object recipe per language and object format

Evidence method: probes outside Bazel with the pinned toolchain (darwin-arm64 bundle clang/lld/llvm-* 23.1.4, the linux-amd64 bundle's sysroot for ELF links) and rustup nightly-2026-10-09; then the real Bazel-built release archives. ThinLTO witness: a C `main` calling one exported function in another module (or the archive); with LTO the body is inlined into `main`, without it `main` calls the archive's machine code.

Evidence (toolchain defaults): the linux sysroot archives are already fat (libz.a members carry `.text` and `.llvm.lto`), and the Elide clang driver passes `--fat-lto-objects` to ld.lld whenever a link has `-flto=thin`, with or without `-ffat-lto-objects`; without `-flto` it does not, so lld links machine code. The darwin sysroot archives are bitcode only (libz.a members are `LLVM bitcode, wrapper`).
Evidence (current release archives, 0.8.0 recipe): `libcsv_archive.a` is 14 bitcode-only members (no machine code), and `libjson_archive.a` holds 6 bitcode-only C++ members beside Rust machine code: under `--features=thin_lto` cc_library objects are bitcode, so today's published static archives only link with an LLVM 23 LTO linker. cc_static_library also collects both `foo.o` and `foo.pic.o` of every translation unit.

Task R1: Ruling: C/C++ on ELF = clang `-flto=thin -ffat-lto-objects` — one object holds `.text` and an `SHT_LLVM_LTO` `.llvm.lto` section (flags `SHF_EXCLUDE`) whose bitcode has a `GLOBALVAL_SUMMARY_BLOCK` (ThinLTO) — cost if wrong: none found; this is upstream LLVM FatLTO.
Evidence: probe `a.o`: `llvm-readobj --sections` lists `.text` and `.llvm.lto` (`SHT_LLVM_LTO`); `llvm-objdump -d` shows `helper` machine code; the dumped `.llvm.lto` is `LLVM IR bitcode` with `GLOBALVAL_SUMMARY_BLOCK`. Linking it from an archive with `-flto=thin` (`ld.lld … --fat-lto-objects -plugin-opt=thinlto`, `--save-temps` writes `lto.elf.lto.libprobe.a(a.o at 84).o`) inlines it: `main: leal (%rdi,%rdi,2),%eax; addl $7,%eax; retq`; without `-flto`: `main: jmp <helper>`.
Task R1: Ruling: C/C++ on Mach-O has no fat object a linker consumes for LTO; ship machine code — cost if wrong: macOS consumers forgo cross-module LTO into our code.
Evidence: `clang -flto=thin -ffat-lto-objects` for arm64-apple-macos: `error: unsupported option '-ffat-lto-objects' for target`; forcing it through `-Xclang`: `fatal error: error in backend: EmbedBitcode pass currently only supports COFF and ELF object formats`. The Apple alternative `-fembed-bitcode` (`__LLVM,__bitcode`) is decorative for LTO: ld64.lld with `-flto=thin` and Apple ld (ld-27106.1) both link it as machine code (`_main: b <_helper>`, no inlining). A bitcode-only archive is not a substitute: Apple clang 21's linker rejects LLVM 23 bitcode (`Invalid summary version 14. Version should be in the range [1-12]`, then segfaults).
Task R1: Ruling: Rust on ELF = build the crates as bitcode (`-Clinker-plugin-lto`; rules_rust already does this for rlibs under `lto=thin`, and `-Clinker-plugin-lto` beside rules_rust's `-Clto=thin` makes the staticlib's own crate bitcode too), then compile that bitcode with the toolchain clang `-O3 -fPIC -flto=thin -ffat-lto-objects -x ir` (the same FatLTO pipeline C/C++ uses); the prebuilt std rlibs' rustc `.llvmbc` bitcode (which has a ThinLTO summary) is compiled the same way; compiler_builtins and its compiler-rt C objects stay machine code — cost if wrong: if a future rustc grows `-Zfat-lto-objects`, the post-processing step is redundant but still correct.
Evidence: nightly-2026-10-09 has no fat-object flag (`rustc -Z help`: only `dylib-lto`, `split-lto-unit`, `thinlto`, `embed-metadata`; `-C embed-bitcode`, `-C linker-plugin-lto`, `-C lto`). `-Cembed-bitcode` is decorative for linker LTO: rustc's `.llvmbc` section (and clang's `-fembed-bitcode` on ELF) is ignored by ld.lld under `-flto=thin` (`main: jmp <helper>`); renaming it to `.llvm.lto` with `SHT_LLVM_LTO` by objcopy is also not picked up. Today's staticlib (`-Clto=thin`) is machine code only for our crates (post-rustc-LTO objects have no bitcode) and `main` calls it under `-flto=thin`. With `-Clinker-plugin-lto` the crate members are raw bitcode with `GLOBALVAL_SUMMARY_BLOCK`; recompiled as above they carry `.text` + `.llvm.lto`, a `-flto=thin` link inlines across C and Rust (`main: jmp <helper::triple_plus>`, `td_entry` inlined) and a plain link calls the machine code (`main: jmp <td_entry>`, empty LTO resolution).
Task R1: Ruling: Rust on Mach-O has no fat format either (same EmbedBitcode limit; rustc's `__LLVM,__bitcode` is not an LTO input); ship machine code, generated by the same bitcode-to-object step without `-ffat-lto-objects` and with `__LLVM,__bitcode` stripped from prebuilt std members — cost if wrong: as for C/C++ Mach-O.
Task R1: Ruling: Rust bitcode members of one input archive are llvm-linked into one module before compiling, so the machine code keeps cross-crate inlining (the default staticlib got it from rustc's ThinLTO); std members stay one fat object each — cost if wrong: a non-LTO consumer that needs any Rust symbol pulls the whole merged module (gc-sections drops the rest), and one action compiles all our Rust at -O3 (minutes, release archives only).
