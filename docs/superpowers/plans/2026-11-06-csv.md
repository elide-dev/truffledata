# CSV Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Record rulings and deviations in a ledger next to this file (`2026-11-06-csv-ledger.md`), in the format of the JSON completion ledger.

**Goal:** Land a strict, streaming RFC 4180 CSV backend that reads generic (all-string) and known-schema (typed) CSV into immutable column batches. Guests read rows through `InteropLibrary` and `DataLibrary`, embedders export rows in one pass, and the backend is measured against stock Java CSV parsers and released as `dev.elide:truffledata-csv`.

**Architecture:** A pure-Java scanner (no native code) reads UTF-8 bytes into a `CsvBatch`. The batch keeps the input `byte[]` and, per column, either a packed span table that points into that input (string columns) or a primitive array (`long[]`, `double[]`, `boolean[]`) filled during the same pass (typed columns). Quoted fields are never copied at ingest. Fields with doubled quotes are unescaped only when read. Batches are immutable and unconfined, need no closing, and are their own snapshot. `CsvRow extends AbstractRow` exports `DataLibrary`, so the core row model (`Schema`, members by header name, elements by ordinal, `ReadLongNode` and the other read nodes) works on CSV rows unchanged. `CsvReader` streams an `InputStream` as a sequence of batches that all share one `Schema` (by identity), with memory bounded by the batch and record limits. `CsvSink` is a flat row/column event interface for one-pass export.

**Tech Stack:** Java 25, Truffle DSL (`data_java_library`: NullAway/JSpecify plus the Truffle processor), the core module (`Schema`, `Field`, `AbstractRow`, `DataLibrary`, `ContractViolation`), GraalVM `25.5.5-elide.24` (SVM runtime-compilation gates with `TRUFFLE_JIT_CHECKS`), and Bazel with Linux amd64 RBE as the default. Benchmarks only: FastCSV `de.siegmar:fastcsv:4.4.0` and Apache Commons CSV `org.apache.commons:commons-csv:1.14.1`.

**Spec:** There is no separate spec; the decisions below are the spec. They follow the conventions of `JSON_PLAN.md` and `docs/superpowers/plans/2026-11-06-json-completion.md`: strictness, no silent fallback, measured claims only, the SVM compiled-read gates, and releases mirroring the JSON artifacts.

## Decisions (with evidence)

### D1. Producer: pure Java, not Rust `csv-core` and not C++

The JSON plan's follow-on note proposed a Rust `csv` producer writing Myna tapes. A throughput probe rejects that hypothesis for CSV. The probes were run on 2026-11-06 on an Apple M5 Max, five or more runs each. They are advisory single-host timings, not harness results, and their sources were scratch files that were not committed.

| Scanner (whole input in memory, records and field spans only) | A: 100 MiB, 8 columns, 9.1 B/field, mixed quoting, doubled quotes, embedded newlines, non-ASCII | B: 100 MiB, 3 columns of ~230 B text, 30% quoted with doubled quotes |
| --- | --- | --- |
| Rust `csv-core` 0.1.13, LTO, `read_record` into a 64 KiB output buffer | 1.25–1.35 GB/s | 2.6 GB/s |
| C++ `-O3` scalar span scanner (quoted runs via `memchr`) | 1.38–1.46 GB/s | 3.2 GB/s |
| C++ with an 8-byte SWAR unquoted-run skip | 1.01 GB/s (slower) | 5.5 GB/s |
| Java scalar span scanner, GraalVM 25 JIT | 1.37–1.41 GB/s | 3.5 GB/s |
| The same Java scanner, SVM AOT `-O3` | 1.20–1.23 GB/s | 2.3 GB/s |
| UTF-8 validation: Rust `str::from_utf8` / Java 8-byte ASCII skip plus scalar DFA | 4.5–5.1 / 4.7 GB/s | — |

With typical short fields, per-field work dominates and Java matches native. Only long unquoted text gains from SIMD or SWAR. That gain is deferred and gated by fixture B in Task 7. Native code would also add:

- a seam ABI, an SVM `@CFunction` backend and a JVM FFM backend; the JVM typed path already copies input into an arena (JSON Task 15 ruling);
- `.so` and `.a` release attachments;
- a Myna tape at 24 B per field, against 8 B per field here;
- for Rust, `myna-values` as a new crate_universe git dependency (it pulls in bumpalo, allocator-api2, serde, json-number and thiserror). `csv-core` also always copies field bytes into its output buffer;
- an untested second Rust staticlib (after Buffa) in the same SVM image, which risks duplicate Rust std symbols.

JSON's own measurements (JSON Task 17 ledger finding) showed the native generic path losing to Gson on retained reads, so the native tier is not an automatic win for read-heavy data. A pure Java backend also runs identically on JVM and SVM from one jar.

### D2. Representation: immutable column batches over retained input

- `CsvBatch` keeps the batch's input `byte[]` (BOM excluded from data, header excluded from rows). Each schema field has one `Column`:
  - STRING: `long[] spans`, one per row. A span packs `(long) offset << 32 | (long) length << 2 | quoted << 1 | escaped`, where `offset` and `length` delimit content with quotes and trimmed blanks excluded.
  - INT64: `long[]`. FLOAT64: `double[]`. BOOLEAN: `boolean[]`.
  - `byte[] states` only when the field is nullable or optional (0 present, 1 null, 2 missing, matching core `Batch.Column`).
- Memory for a generic batch is the input plus 8 B per field plus array headers. Typed columns cost 8 B (or 1 B) per cell, and their text is not retained separately: the input stays retained for the string columns.
- Generic mode is the typed mode with a schema of STRING fields derived from the header (or named `"0"`..`"n-1"` without a header). One representation serves both.
- Rows are views: `CsvRow(batch, index)`. Rows created in compiled code are virtualized.
- Deferred:
  - Myna tapes for CSV.
  - Writing into core `Batch` (it boxes FLOAT64 and BOOLEAN, and has no text column); a follow-on can move primitive and text columns into core.
  - Adopting off-heap or mmap input.
  - Buffer recycling across batches. It would make batches scoped and require an owner.

### D3. Strict input contract ("simple")

- RFC 4180 records: delimiter, quote and doubled-quote escape, and quoted fields may contain the delimiter, CR and LF.
- Accepted terminators are CRLF, LF and lone CR, matching `csv-core` and Python. A final record may omit its terminator. Completely empty lines (zero bytes between terminators) are skipped.
- Strict by default:
  - A quote inside an unquoted field is rejected ("bare quote").
  - Bytes between a closing quote and the next delimiter or terminator are rejected (except blanks when `trim`).
  - An unterminated quote at end of input is rejected.
- Ragged rows are rejected unless `flexible`. Flexible allows only shorter rows: the missing trailing fields read as `Missing`. Longer rows are always rejected.
- A UTF-8 BOM (`EF BB BF`) at stream start is skipped. All batch bytes must be valid UTF-8 under the strict rules: no overlongs, no surrogates, nothing above U+10FFFF, and no truncated sequence at end of input.
- `trim` strips ASCII space and tab around unquoted content, and outside the quotes of quoted fields.
- Options: delimiter and quote (single ASCII bytes, never CR or LF, distinct from each other), `quoting` on or off, `header` (default on), `trim` (default off), `flexible` (default off).
- Deferred: backslash escapes, comment lines, multi-byte delimiters, null tokens (`NA`, `\N`), encodings other than UTF-8, and type inference.

### D4. Limits

`CsvLimits(maxBatchBytes = 64 MiB, maxRecordBytes = 1 MiB, maxColumns = 4096, maxBatchRows = 1,048,576)`.

- `parse(byte[])` checks `maxBatchBytes` before copying.
- Streaming holds at most one batch buffer and one incomplete record. An incomplete record longer than `maxRecordBytes` fails, so an unterminated quote cannot grow memory without bound.
- Errors:
  - Syntax, UTF-8 and limit failures are `IllegalArgumentException`, with messages `"CSV syntax at record R, byte B: <reason>"` and `"CSV resource limit: <name>"`.
  - Typed contract failures are `ContractViolation`, which extends `IllegalArgumentException`. Its messages name the record and column and never include field values (core convention).
  - `CsvReader.next()` propagates `IOException`.

### D5. Typed conversions (exact grammar, no inference)

| Kind | Accepted content | Notes |
| --- | --- | --- |
| INT64 | `-?[0-9]+`, within int64 | Leading zeros allowed. `+`, blanks (without `trim`) and overflow are rejected. Width and range constraints are checked with `Values.validateLong`. |
| FLOAT64 | `[+-]?([0-9]+(\.[0-9]*)?\|\.[0-9]+)([eE][+-]?[0-9]+)?` | Correctly rounded. Clinger fast path: when the mantissa is ≤ 2^53 and the decimal exponent is within ±22, the result is exact. Otherwise fall back to `Double.parseDouble` on a Latin-1 `String`, which allocates. Non-finite results are rejected, `-0` gives `-0.0`, and `floatBits == 32` requires an exact binary32. |
| BOOLEAN | `true` or `false`, ASCII case-insensitive | Anything else is rejected. |
| STRING | any validated UTF-8 | Length constraints are rejected at compile time (deferred). |
| EXACT, ARRAY, RECORD, ANY | — | Rejected at compile time. |

- A field is null only when it is unquoted, empty and in a nullable column. `""` is an empty string for STRING and a conversion error for other kinds. A non-nullable STRING reads an unquoted empty field as `""`.
- With `header`, header names map to schema fields by exact name. Header columns not in the schema are skipped (projection). A schema field absent from the header fails at the header unless it is `optional`, in which case every row reads `Missing`. A schema field matched by two header columns fails.
- Without `header`, columns map by position, and the record width must equal `schema.size()`. With `flexible`, shorter rows are allowed when every absent field is optional.

### D6. Shared abstractions and the JSON performance plan

CSV consumes but does not modify:

- core `Schema`, `Field`, `AbstractRow`, `DataLibrary`, `Missing`, `DataNull`, `ContractViolation`, `Values.validateLong`, and the `Read*Node`s;
- the comparison harness pattern (`JsonComparison`, `json_smoke.py`);
- `TRUFFLE_JIT_CHECKS`;
- the release macros.

CSV does **not** touch `JsonOwner`, `JsonValue`, `JsonSink`, Myna tapes or seam files. The `JsonOwner → TapeOwner` generalization stays with YAML and the JSON performance plan, and nothing here precludes it: YAML can still be a Myna tape producer behind a shared owner and sink.

Shared-interface candidates to settle with the JSON performance plan (not implemented here):

1. A backend-neutral UTF-8 text view. `CsvText` here plays the role `JsonValue` plays for `JsonSink` string and key events.
2. A tree-shaped sink, so that one embedder sink can consume JSON, YAML and CSV (as an array of objects).
3. Primitive and text columns in core `Batch`.
4. The scanner-parity evidence in D1, which bears on any small-input JSON path.

## Global Constraints

- No native code, seam, FFM or `@CFunction` in `//csv`. One jar serves JVM and SVM. Nothing falls back to another parser.
- Batches, rows and plans are immutable and safe to share across threads. `CsvReader` is single-threaded and owns its stream.
- `CsvBatch` arrays are never exposed. `CsvText` is a reusable view, valid only during the sink call that receives it.
- All batches from one `CsvReader` or `CsvPlan` share one `Schema` instance. Compiled caches key on schema identity (core `Schema` contract).
- Every exported message or read that runs in compiled code avoids instance `@TruffleBoundary` methods that return fresh views. Slow paths are static boundaries (JSON Task 9 ruling). If SVM reports "reachable during compilation, but was not seen during Bytecode parsing" for a trivial accessor, inline the field read at the call site (JSON Task 9 ruling) rather than adding boundaries to hot messages.
- Java sources compile under NullAway/JSpecify (`@NullMarked` `package-info.java`) and the Truffle DSL processor via `data_java_library`.
- JVM tests: `bazel test //csv/tests:jvm`. SVM tests are `manual`, Linux x86_64 only, through RBE: `bazel test //csv/tests:native_test`.
- Compiled gates (as in JSON):
  - observed compiled execution;
  - `compiler.TreatPerformanceWarningsAsErrors=all`;
  - Graal graphs of at most 10,000 nodes and ASTs of at most 192 nodes;
  - at most **0.05 Java bytes per read** for typed primitive reads and for row iteration that ends in a primitive read;
  - at most 0.05 B per row for the export walk with a non-allocating sink.
- Performance claims come only from `//benchmarks/comparison:csv_measure`, with raw samples kept under `benchmarks/results/csv-<sha>/`. Targets below are hypotheses until measured.
- Commit messages use the repository prefixes (`feat:`, `perf:`, `test:`, `build:`, `docs:`) and end with a blank line then `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A record cut by a streaming buffer boundary** must not be split or misread. This covers a cut between the two quotes of `""`, right after an opening quote, between CR and LF, and inside a multi-byte UTF-8 sequence. At every cut position the rows must equal the whole-input parse. Pinned by Task 3's `CsvReaderTest.everyCutPositionMatchesWholeParse` and `CsvReaderTest.multibyteSequenceSplitAcrossReads`.
2. **A quote byte at the end of a non-final buffer** must be reported as incomplete, never as a closing quote. Likewise a CR, and an unterminated last field without EOF. Pinned by Task 1's `CsvScannerTest.ambiguousTailIsIncomplete`.
3. **`"say ""hi"""` reads `say "hi"`** on every path: `CsvRow.getString`, `DataLibrary.read`, interop `asString`, `CsvText` in export, and header names. Unescaped quoted fields reference the input without a copy. Pinned by Task 2's `CsvBatchTest.escapedFieldIsUnescapedOnEveryPath` and Task 5's `CsvExportTest.escapedTextUsesScratchOnly`.
4. **Typed conversions never accept silently.** Cases:
   - `9223372036854775808`, `+1`, ` 42` (without `trim`), `1e400` and `NaN` are rejected;
   - `""` in a nullable INT64 is rejected, while an unquoted empty field is null;
   - FLOAT64 matches `Double.parseDouble` bit for bit, both on the fast path and on 17-digit and subnormal tokens.

   Pinned by Task 4's `CsvPlanTest.conversionBoundaries` and `CsvPlanTest.fastPathMatchesParseDouble`.
5. **An unterminated quote in an endless stream** must fail at `maxRecordBytes` with bounded memory, not buffer the stream. Pinned by Task 3's `CsvReaderTest.unterminatedQuoteFailsAtRecordLimit`.
6. **Compiled typed reads across batches from one reader** must stay monomorphic and allocation-free (≤ 0.05 B per read), including rows produced by interop `readArrayElement` in the loop. Pinned by Task 6's `CompiledReads` gate in `//csv/tests:native_test`.

```java
public record CsvFormat(byte delimiter, byte quote, boolean quoting, boolean header, boolean trim, boolean flexible) {
  public static final CsvFormat RFC4180 = new CsvFormat((byte) ',', (byte) '"', true, true, false, false);
  // Compact constructor: delimiter and quote in 0x01..0x7F, neither CR nor LF, delimiter != quote,
  // and trim forbids a space or tab delimiter.
  public CsvFormat withDelimiter(char c); public CsvFormat withQuote(char c); public CsvFormat withoutQuoting();
  public CsvFormat withHeader(boolean h); public CsvFormat withTrim(boolean t); public CsvFormat withFlexible(boolean f);
}
public record CsvLimits(int maxBatchBytes, int maxRecordBytes, int maxColumns, int maxBatchRows) {
  public static final CsvLimits DEFAULT = new CsvLimits(64 << 20, 1 << 20, 4096, 1 << 20);
  // All positive; maxRecordBytes <= maxBatchBytes; maxBatchBytes <= Integer.MAX_VALUE - 64;
  // maxRecordBytes < 1 << 30 (the span length field).
}
final class Utf8 {
  /** -1 when [from, to) is strict UTF-8, else the offset of the first invalid or truncated sequence. */
  static int invalidOffset(byte[] bytes, int from, int to);   // 8-byte ASCII skip via a little-endian long VarHandle
}
final class CsvScanner {
  /** One complete, non-empty record. Spans use the D2 packing; spans has length >= count. */
  interface Records { boolean record(long[] spans, int count, int start, int end); } // false: stop before this record
  CsvScanner(CsvFormat format, CsvLimits limits);
  /**
   * Scans complete records in [from, to) and returns the offset after the last record consumed.
   * Without eof, a record that could continue past `to` is not reported and its start is returned:
   * an open quote, a final quote byte inside a quoted field, a final CR, or a missing terminator.
   * With eof, a final unterminated record is reported and an open quote throws.
   * More than maxColumns fields throws the columns limit.
   */
  int scan(byte[] input, int from, int to, boolean eof, Records records);
}
```

The scanner keeps one reusable `long[]` of current-record spans, which grows up to `maxColumns`. It never allocates per record or per field. Errors carry the record ordinal within the scan and the byte offset. Callers add the stream base (Task 3).

### Task 3: Streaming reader

**Files:**
- Create: `csv/src/main/java/dev/elide/truffledata/csv/CsvReader.java`.

**Interfaces:**

```java
public static CsvReader open(InputStream input, CsvFormat format);                                    // in Csv
public static CsvReader open(InputStream input, CsvFormat format, CsvLimits limits, int batchBytes);  // batchBytes default 1 MiB
public final class CsvReader implements AutoCloseable {
  public Schema schema() throws IOException;          // reads the header on first call; same instance for every batch
  public @Nullable CsvBatch next() throws IOException; // >= 1 row, or null at end of input
  public long records();                               // data records returned so far
  public long position();                              // stream bytes consumed into returned batches (BOM and header included)
  @Override public void close() throws IOException;    // closes the stream; idempotent
}
```

Algorithm:

1. Allocate a fresh `byte[]` per batch (`batchBytes` plus the carried bytes).
2. Copy the previous incomplete record to the front.
3. Fill until the buffer is full or the stream ends.
4. `scan(eof)`, then `Utf8.invalidOffset` over the consumed range only. A sequence cut at the tail is checked with the next batch.
5. If nothing completes and not at EOF, double the buffer, up to `maxRecordBytes` plus 1 for the incomplete record. Past that, throw `"CSV resource limit: maxRecordBytes"`.
6. Stop the batch at `maxBatchRows`, carrying the rest.

The batch keeps its buffer; there is no reuse. Error offsets are stream offsets.

## Deferred (with triggers)

- **SWAR or SIMD unquoted-run skip** in the Java scanner. Trigger: H3 below 1.5×. Measure Java first, using a little-endian `long` VarHandle. Consider a native scanner only if Java cannot close the gap, behind the same `CsvScanner` contract.
- **Off-heap and mmap adoption, and buffer recycling.** Either one makes batches scoped. At that point introduce a shared scoped owner, coordinated with the JSON performance plan's owner decisions.
- **More strictness options:** null tokens, wider boolean spellings, STRING length constraints, comments, backslash escapes, other encodings.
- **Core `Batch` primitive and text columns**, so CSV and JDBC share column storage.
- **A tree-shaped shared sink and a neutral UTF-8 text view** (D6), CSV writing, and CodSpeed `cases.json` entries.
